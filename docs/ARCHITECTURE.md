# Pomb architecture

A map of the code. Update it in the same change that adds, moves or removes a module.


- `src/main.rs`: CLI (`--auth`/`--mode`/`--host`/`--port`/`--database-path`/`--backup-dir`/`--public-url`/`--trust-proxy`, env-overridable), startup.
- `src/routes.rs`: all routes + handlers + Askama templates wiring.
- `src/routes/slot.rs`: the slots that let a few attachment uploads, downloads and whole-board reads (the board page and the calendar feed) run at once, each request holding one of its account's slots (taken after the task or board is resolved to that account) and one of the server's, and `SlotBody`, the response body that sends bytes or streams a file and frees its slots when it is sent or after 120 seconds. `src/routes/export.rs`: `TaskStream`, the board export body that sends one task at a time.
- `src/db/events.rs`: the board event stream. Every task add, move, rename, resize, relabel and re-description and every new comment writes a `BoardEventRow` into the table `board_events`, keyed by board id and a sequence number that counts up per board, in the same transaction as the change. A board keeps its newest `MAX_EVENTS_PER_BOARD` (1000) events, and a read from a cursor older than the oldest kept is `EventRead::Expired`. The commit of a transaction that wrote events wakes the waiters through the table `event_wakeups` and `Store::wake`. `src/routes/slot.rs` holds the wait guard (`WaitGuard`) of `GET /api/boards/{id}/events/wait`: a wait takes one `AccountSlot::TokenWait` slot of its token (`WAITS_PER_TOKEN_AT_ONCE`, 16) and one `AccountSlot::Wait` slot of its account (`WAITS_PER_ACCOUNT_AT_ONCE`, 32), and a wait past either is answered 429 `too_many_waits`.
- `src/search.rs`: the query language behind `GET /api/search`. `Query::parse` turns `q` into words, quoted phrases and `in:`, `board:`, `column:`, `label:`, `color:` and `is:` filters; `Query::find` tests one card against a `BoardView` and returns a `Hit` with its status, matched field and character ranges; `Hit::rank` orders hits by status, field, score, name and id. The handler in `src/routes.rs` reads each board the credential may reach in one transaction and stops at a 2 second budget.
- `src/db.rs`: redb tables (`*_by_*` multimaps are secondary indexes). Every board, token,
  saved template and time entry belongs to an account; `src/db/` holds the three handles the
  routes reach data through: `AccountDb` (one account's rows, by `Owned*` proofs), `InstanceDb`
  (instance settings, invites and the account list, no board content) and `PublicDb` (sign-in, setup, invite
  registration, recovery, device pairing, the calendar feed). `src/db/membership.rs` holds the
  instance mode, invites, registration and its approval, suspension, recovery codes and account
  deletion, `src/db/activity.rs` when each account was last seen and each board last used, and
  `src/db/prune.rs` the daily deletion of unused member boards and the accounts it leaves empty, and `src/db/usage.rs` the bytes each account stores, which every task, template and attachment write keeps in step through `txn_store_task`. `src/db/entries.rs` indexes each account's time entries in the multimaps `entries_by_account` and `entries_by_day` (keyed `account|UTC day`), which every entry write keeps in step through `txn_store_entry` and `txn_remove_entry`, and holds the time entry quota and the per-day cap. The multimap `passkeys_by_user` indexes each account's passkeys (at most 10, recovery excepted), the table `passkeys_by_credential` maps each credential id to its passkey, the multimaps `tokens_by_account`, `sessions_by_user` and `devices_by_account` index each account's tokens (live and suspended), sessions and approved device requests, so registration's duplicate check and account deletion never scan those tables, the table `token_ids_by_hash` maps the SHA-256 of each API token (live or suspended) to its id so a Bearer request never scans the tokens, the multimap `salted_tokens_by_last4` finds a token that predates it and still holds a salted hash (it is keyed the first time it authenticates), the multimap `devices_by_user_code` finds a device request by its user code, the multimap `devices_by_expiry` finds the live and the stale ones by their expiry so creating a request never scans the table, and the table `feed_tokens` maps the SHA-256 of each calendar-feed token to its board, kept in step by every board write through `txn_store_board`.
- `src/disk.rs`: `DiskGuard`, which stops writes that grow the database while it or its file holds more than its size limit, the disk is below its free space floor, or no measurement is younger than 60 seconds. It measures every 10 seconds on a blocking thread, a write that finds the sample older starts one more there, and no request ever measures or takes the writer. The `Writes` flag of each `ROUTE_ACCESS` entry says which routes it stops. Quotas, rate limits and the `DiskLimits` are `InstanceSettings` fields the admin edits.
- `src/backup.rs`: consistent snapshots of the database and its attachment files (a held write transaction), the `pomb-<stamp>.attachments` copy beside each backup that rotation deletes with it, and the schedule; the settings and last status are `BackupSettings` and `BackupStatus` rows in the `settings` table.
- `src/auth.rs`: sign-in modes (`--auth none|passkey`), session cookies, API tokens. The table `sessions` is keyed by the SHA-256 of the cookie value, so a backup holds no value that signs a browser in; session creation refuses an absent or suspended account inside its write transaction, and finishing recovery revokes the account's tokens, other passkeys and sessions, and denies its approved device requests, in the one that commits it.
- `src/passkey.rs`: the WebAuthn relying party (webauthn-rs) and its pending ceremonies.
- `src/models.rs`: shared domain types.

- `src/archive.rs`: the board archive. `Archive` produces a gzipped tar of `board.json` and the attachment files chunk by chunk, and `archive_database` writes one per board for `pomb archive --database-path FILE --out DIR`, offline and read-only. `src/archive/tar.rs` is its ustar and PAX writer and reader, and `src/archive/import.rs` with `src/db/import.rs` turns an archive into a new board.
- `src/routes/export.rs`: `Pieces` is an export's content as pieces, `Streamed` the body that sends them (it holds an optional slot and stops after 120 seconds), and `TaskStream` and `ArchiveStream` the board export and board archive bodies.
- `src/db/snapshot.rs`: `BoardSnapshot` is one board read through one transaction, and `OfflineDb` a read-only open of the database file for the CLI.
- `src/db/files.rs`: `AttachmentFiles`, the `<database file>.attachments` directory beside the database that holds each attachment's bytes in a file named by its generated UUID (any other id is refused). A write goes to a `.part` file, is flushed and renamed before its row commits, a delete unlinks after its transaction commits, and the startup check removes leftover `.part` files, keeps and reports the files no task names, and reports the tasks whose file is missing. `Db::open` first moves the rows of the old `attachment_data` table into files and deletes the table in one transaction after the last file, and `OfflineDb` refuses a file that still has it. `Incoming` receives an upload chunk by chunk into a `.part` file that is placed only after the last chunk, and a download opens the file and streams it.
- `src/taskjson.rs`: `TaskArray` writes a JSON object ending in a `tasks` array, piece by piece.
- `src/client.rs`: `Client`, a blocking ureq client of a running server built from `POMB_URL` and `POMB_API_TOKEN`. It sends the token as a Bearer header, turns a status of 400 or more into an `Error`, and redacts the token from every error text and its `Debug`.
- `src/board_cli.rs`: the `pomb board` verbs `ls`, `show`, `add`, `move`, `note`, `outcome`, `link`, `label` and `attach`, run before the server starts. `run` returns the text to print. `board_cli/wire.rs` holds the small response structs and `board_cli/table.rs` the aligned plain output.
- `.dev/site/`: the hosting of the public sites, run as `dev site <verb>`. The verbs are `deploy`, `verify`, `status`, `provision`, `launch`, `restage`, `setup-code` and the hidden `decoys`, over ssh with the key `~/.ssh/pomb_app` (`POMB_KEY` overrides it). `__common.sh` reads the box's `user@host` at run time from `pass show Agents/Linode/pomb.app-host`, and `provision` fills the `@ADMIN_IP@` placeholder of `sshd/10-pomb.conf` (the `PerSourcePenaltyExemptList`) from `pass show Agents/Linode/pomb.app-admin-ip` in a staged copy; a missing entry fails the verb, and no address is ever committed. The box files are `apt/`, `sshd/`, `systemd/`, `env.in`, `setup.sh` (the idempotent box setup) and `pomb-update`, the pull agent a systemd timer runs as `pomb-update <stable|nightly> [<tag>]`: for a new release it downloads and checks the binary, stops the unit and copies the database to `backups/pomb-<UTC>-before-<id>.redb`, swaps the binary and restarts, and if the health check fails it restores the copy and the previous binary and does not retry that release. Once the unit runs again it runs `pomb archive` on the copy with the previous binary, writing one `.tar.gz` per board into `pomb-<UTC>-before-<id>.archives/` (a binary older than 0.5.30 has no `archive`, and a failure or 60 seconds only logs a warning), and it keeps the last 3 copies with their archive directories. `dev site verify` checks a channel after an update: the public build_sha, `/login` and `/setup`, the CSP and HSTS headers, the journal since the unit started, `last-update-<channel>` and the pre-update backup.
