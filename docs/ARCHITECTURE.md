# Pomb architecture

A map of the code. Update it in the same change that adds, moves or removes a module.


- `src/main.rs`: CLI (`--auth`/`--mode`/`--host`/`--port`/`--database-path`/`--backup-dir`/`--public-url`/`--trust-proxy`, env-overridable), startup.
- `src/rules.rs`: the per-board column rules kept in the board config under `column_rules`: the labels that lock a card against a token without `tasks.edit_locked`, a grant-only permission that no preset holds and the owner's browser session does and, per column id, the sections, outcome range and fields a task needs to enter it, and `role_moves`, where each agent role id may move a task out of a column and into which columns. `violations` checks a task, `ColumnRules::validated` checks a saved rule set, and `ColumnRules::role_targets` answers a bearer move: a token issued as a role is held to the stored moves, or, when the board stores none, the standard roles to the standard pull-model moves out of every column, resolved onto the columns whose `stage` (a `ColumnStage` the owner sets in the Edit column dialog, filled from the old names once at schema 79) is in_progress, review, verify, release or ready, the board's Blocked column and its Done columns, and no rule where the stage columns are missing, so a board with no stages has no standard limits. `move_task`, the bulk move and a question's answer refuse a forbidden move with 403 `role_move_forbidden`. The owner's browser session and a token with no role are never limited.
- `src/layouts.rs`: the built-in board layouts (name, category, description, columns) and the categories the Create board page groups them by. `Db::ensure_builtin_templates` seeds each layout as a built-in template, and `category_of` names the category of a built-in template.
- `src/labels.rs`: the per-board label settings kept in the board config under `label_settings`: the highlighted labels with a colour each, the show-all flag and the labels kept with no card. `LabelSettings::validated` checks a saved set; `Db::board_label_counts` adds the kept labels to the counts of the tasks' labels.
- `src/routes.rs`: all routes + handlers + Askama templates wiring.
- `src/auth.rs` `required_role`: the lowest `BoardRole` each route accepts. The `AccountDb` extractor carries it, a lower role is refused with `RoleDenied` as a 403, and a board the account holds no role on stays a 404. Time entries stay per account on a shared board.
- `src/routes/slot.rs`: the slots that let a few attachment uploads, downloads and whole-board reads (the board page and the calendar feed) run at once, each request holding one of its account's slots (taken after the task or board is resolved to that account) and one of the server's, and `SlotBody`, the response body that sends bytes or streams a file and frees its slots when it is sent or after 120 seconds. `src/routes/export.rs`: `TaskStream`, the board export body that sends one task at a time.
- `src/db/events.rs`: the board event stream. Every task add, move, rename, resize, relabel and re-description and every new comment writes a `BoardEventRow` into the table `board_events`, keyed by board id and a sequence number that counts up per board, in the same transaction as the change. A board keeps its newest `MAX_EVENTS_PER_BOARD` (1000) events, and a read from a cursor older than the oldest kept is `EventRead::Expired`. The commit of a transaction that wrote events wakes the waiters through the table `event_wakeups` and `Store::wake`. `src/routes/slot.rs` holds the wait guard (`WaitGuard`) of `GET /api/boards/{id}/events/wait`: a wait takes one `AccountSlot::TokenWait` slot of its token (`WAITS_PER_TOKEN_AT_ONCE`, 16) and one `AccountSlot::Wait` slot of its account (`WAITS_PER_ACCOUNT_AT_ONCE`, 32), and a wait past either is answered 429 `too_many_waits`.
- `src/image.rs`: `sniff` reads the type (PNG, JPEG, WebP or GIF, never SVG) and the declared size of an image from its first bytes alone, and refuses one over 8000 pixels on a side or 40 megapixels. `GET /api/tasks/{id}/attachments/{attachment_id}/image` in `src/routes.rs` serves an attachment that passes it inline under the sniffed type, with `nosniff` and a `sandbox; default-src 'none'` policy that `security_headers` leaves as the handler set it.
- `src/search.rs`: the query language behind `GET /api/search`. `Query::parse` turns `q` into words, quoted phrases and `in:`, `board:`, `column:`, `label:`, `color:` and `is:` filters; `Query::find` tests one card against a `BoardView` and returns a `Hit` with its status, matched field and character ranges; `Hit::rank` orders hits by status, field, score, name and id. The handler in `src/routes.rs` reads each board the credential may reach in one transaction and stops at a 2 second budget.
- `src/db.rs`: redb tables (`*_by_*` multimaps are secondary indexes). Every board, token,
  saved template and time entry belongs to an account; `src/db/` holds the three handles the
  routes reach data through: `AccountDb` (one account's rows, by `Owned*` proofs), `InstanceDb`
  (instance settings, invites and the account list, no board content),
  `SettingsDb`, which wraps it for the four backup routes and which an Admin preset token of the
  admin account reaches too, `RootAdminDb`, which wraps it for the invite and sign-up approval
  routes and which only a root Admin preset token of the admin account reaches besides its
  browser session, and `PublicDb` (sign-in, setup, invite
  registration, recovery, device pairing, the calendar feed). `src/db/membership.rs` holds the
  instance mode, invites, registration and its approval, suspension, recovery codes and account
  deletion, `src/db/sharing.rs` the accounts that joined a board they do not own: the table `board_members` (keyed `<board id>|<account id>`, one `BoardMemberRow` with a viewer or member `BoardRole`) and the multimaps `members_by_board` and `boards_by_member`, which board and account deletion keep in step, while the board's `owner_id` still names its owner (handing a board over moves that id, the board's counted bytes and its place in `boards_by_owner` in one transaction), `src/db/bin.rs` the recycle bin (deleted tasks, whole, until restored or purged after 30 days), `src/db/activity.rs` when each account was last seen and each board last used, and
  `src/db/prune.rs` the daily deletion of unused member boards and the accounts it leaves with neither a board nor a role on one, `src/db/notifications.rs` the table `notifications` (each account's notifications, newest 500 kept, written by `txn_store_task` for token changes and by `Db::notify` for column, board and task-delete changes, skipping the kinds the account muted in its settings; the routes `/api/notifications` (`notifications.read` and `settings.write`) list and mark them read), and `src/db/avatar.rs` the table `avatars` (each account's uploaded avatar image, written with the avatar kind in one transaction, counted against the account's stored bytes, and dropped by any settings write that makes the avatar text), and `src/db/usage.rs` the bytes each account stores, which every task, template and attachment write keeps in step through `txn_store_task`, and `LargestUse`, the most one account, one board and one attachment file hold, which the admin page shows beside the limits (the `stored_mib_per_board` quota and the admin's `max_attachment_mib` are checked from the board's tasks and its recycle bin, not from a counter). `src/db/entries.rs` indexes each account's time entries in the multimaps `entries_by_account` and `entries_by_day` (keyed `account|UTC day`), which every entry write keeps in step through `txn_store_entry` and `txn_remove_entry`, and holds the time entry quota and the per-day cap. The multimap `passkeys_by_user` indexes each account's passkeys (at most 10, recovery excepted), the table `passkeys_by_credential` maps each credential id to its passkey, the multimaps `tokens_by_account`, `sessions_by_user` and `devices_by_account` index each account's tokens (live and suspended), sessions and approved device requests, so registration's duplicate check and account deletion never scan those tables, the table `token_ids_by_hash` maps the SHA-256 of each API token (live or suspended) to its id so a Bearer request never scans the tokens, the multimap `salted_tokens_by_last4` finds a token that predates it and still holds a salted hash (it is keyed the first time it authenticates), the multimap `devices_by_user_code` finds a device request by its user code, the multimap `devices_by_expiry` finds the live and the stale ones by their expiry so creating a request never scans the table, and the table `feed_tokens` maps the SHA-256 of each calendar-feed token to its board, kept in step by every board write through `txn_store_board`.
- `src/disk.rs`: `DiskGuard`, which stops writes that grow the database while it or its file holds more than its size limit, the disk is below its free space floor, or no measurement is younger than 60 seconds. It measures every 10 seconds on a blocking thread, a write that finds the sample older starts one more there, and no request ever measures or takes the writer. The `Writes` flag of each `ROUTE_ACCESS` entry says which routes it stops. Quotas, rate limits and the `DiskLimits` are `InstanceSettings` fields the admin edits.
- `src/backup.rs`: consistent snapshots of the database and its attachment files (a held write transaction), the `pomb-<stamp>.attachments` copy beside each backup that rotation deletes with it, and the schedule; the settings and last status are `BackupSettings` and `BackupStatus` rows in the `settings` table.
- `src/auth.rs`: sign-in modes (`--auth none|passkey`), session cookies, API tokens. The table `sessions` is keyed by the SHA-256 of the cookie value, so a backup holds no value that signs a browser in; session creation refuses an absent or suspended account inside its write transaction, and finishing recovery revokes the account's tokens, other passkeys and sessions, and denies its approved device requests, in the one that commits it. Each session stores a device label (browser and system) read from the sign-in's `User-Agent` and no IP address. The sessions list on the settings page names a session by the first 16 characters of its key, and `DELETE /api/v1/auth/sessions/{id}` ends any session of the account but the one asking.
- `src/passkey.rs`: the WebAuthn relying party (webauthn-rs) and its pending ceremonies.
- `src/models.rs`: shared domain types.

- `src/archive.rs`: the board archive. `Archive` produces a gzipped tar of `board.json` and the attachment files chunk by chunk, and `archive_database` writes one per board for `pomb archive --database-path FILE --out DIR`, offline and read-only. `src/archive/tar.rs` is its ustar and PAX writer and reader, and `src/archive/import.rs` with `src/db/import.rs` turns an archive into a new board.
- `src/routes/multipart.rs`: `Multipart`, the streaming reader of a multipart/form-data upload, which holds one chunk and a boundary in memory and hands each part's data to the upload route as it arrives.
- `src/routes/calendar_export.rs`: the due date export behind `GET /api/calendar-export`. `due_rows` collects the task and subtask due dates of the named boards that fall in a day range, `csv_bytes` writes them as quoted CSV and `xlsx_bytes` as a one-sheet Excel workbook inside a stored zip it writes itself (checksums from `flate2::Crc`), so no zip crate is needed.
- `src/routes/board_history.rs`: the rows behind `GET /api/boards/{id}/history`. `page` collects one row for each event, comment and recycle bin task of a board, keeps the ones a `Filter` (event group, kind of change, user, time range) passes, sorts them newest or oldest first and lists the users on the board; `export_cells` shapes them for the Excel and CSV files, which `src/routes/calendar_export.rs` writes.
- `src/routes/local_time.rs`: `LocalTime`, a clock time the server renders as a `<time>` element holding the UTC instant in `data-at`, the shape in `data-fmt` and the account's 12 or 24 hour clock in `data-clock`, with a fallback text in UTC marked "UTC".
- `static/pure.js`: `LocalTime` and `isoDate`, the browser helpers that touch no page state. `LocalTime` rewrites each `<time>` element the server renders, and every element a swap inserts, in the browser's zone on load, and `tests/js/local_time.js` covers its formats. `templates/base.html` loads it before `static/app.js`, which hands `LocalTime` the account preferences with `LocalTime.use`, and the `tests/js` scripts load it with `require`.
- `src/routes/export.rs`: `Pieces` is an export's content as pieces, `Streamed` the body that sends them (it holds an optional slot and stops after 120 seconds), and `TaskStream` and `ArchiveStream` the board export and board archive bodies.
- `src/db/agents.rs`: an account's agent roles, each a name and a permission template under an id that never changes, in the tables `agent_roles` and `agent_role_grants` with the multimaps `agent_roles_by_account`, `agent_role_grants_by_board` and `agent_role_grants_by_role`, at most 50 roles per account (checked in the insert's write transaction) and a name unique on the account. A grant ties a role to a board of its account, and `txn_remove_board`, a board owner change and `txn_delete_account` drop the grants and roles they strand. Every account gets the standard roles with no board granted when it is created and, once, when an upgraded file holds none (`txn_seed_standard_roles`), and a deleted one is not re-added. Only the owner's browser session creates or edits a role, through `/api/v1/agent-roles`, and a token with `roles.read` reads them. A token with `roles.grant` (the lead preset) creates the six standard roles the account lacks through `POST /api/v1/agent-roles/standard` and grants a role a board through `PUT /api/v1/agent-roles/{id}/boards/{board_id}`, each only for boards the token holds (`exceeds_grant` otherwise). `AgentRoleRow.issued` counts the tokens a role has issued, and `Db::create_api_token_as_role` bumps it and stamps the token with `role_id`, `role_name` and the label `agent-N` in one write transaction, so a label is never reused and a rename leaves the snapshot as issued. A request reads only the token row, never the role.
- `src/db/webhooks.rs`: a board's webhooks in the table `webhooks` and the multimap `webhooks_by_board`, at most 20 per board (checked in the insert's write transaction), each with a name, an `http` or `https` URL, event names, an optional column filter, an enabled flag and a secret made at creation. Webhook rows are counted in each account's stored bytes, removed with their board by `txn_remove_board`, and left out of board exports, archives and snapshots so a secret never leaves the server. They are managed through `/api/boards/{id}/webhooks` and `/api/webhooks/{id}` (permission `webhooks.manage`).
- `src/db/inbound.rs`: a board's inbound email addresses in the table `inbound_addresses`, the multimap `inbound_by_board` and the table `inbound_by_hash` (the SHA-256 of an address to its id), at most 20 per board (checked in the insert's write transaction). An address is an optional prefix and 64 hex characters of randomness. Create and rotate return it once and only its hash is stored, and a lookup goes by the hash and confirms it in constant time. Rows count toward the owner's stored bytes, go with their board or with the column they name, and stay out of exports.
- `src/db/limit_groups.rs` and `src/routes/limit_groups.rs`: a board's limit groups, each one card limit shared by a run of adjacent columns, stored as `BoardRow.limit_groups` (a `LimitGroup` holds an id, the column ids in board order and the limit, at most 20 per board, a column in at most one). `LimitGroup::check` refuses a limit under 1, fewer than two columns, a column listed twice, off the board or in another group, and columns that are not adjacent, which the create and change handlers answer with 400. `move_in` refuses a move into a grouped column from outside its group with `MoveOutcome::GroupLimit` (409 `wip_limit_reached`) when the group already holds its limit in cards, on top of the column's own limit and under the same enforce switch (`force` skips both), and a deleted column leaves its group in the delete's transaction. A column move that would split a group is refused with 400. The routes `POST /api/boards/{id}/limit-groups` and `PATCH` and `DELETE /api/boards/{id}/limit-groups/{group_id}` need `columns.edit`, `GET /api/boards/{id}` lists each group with its `count`, and the board archive carries the groups in `limit_groups`.
- `src/routes/inbound.rs`: the create, list, rotate and delete handlers for inbound addresses under `inbound.manage`, the views that never carry an address except in the create and rotate responses, and `POST /api/inbound/{address}`, the public route that turns a forwarded mail into a task. That route looks the address up through `PublicDb::inbound_grant`, limits unknown addresses per client (`IpScope::InboundMiss`) and each address by its own bucket (`Limits::check_inbound`), and reads the body only up to 1 MiB. The Add task from email tab of `templates/board_settings.html` (`board-settings-inbound` in `static/pages.js`) manages them.
- `src/db/outbox.rs`: the delivery outbox in the table `webhook_outbox` (key: a zero-padded global sequence, so the oldest event sorts first) and the multimap `webhook_outbox_by_hook`. `txn_store_task` calls `txn_queue_events` with the board events it records, and `Db::delete_task` calls `txn_queue_task_deleted`, so every event is queued in the write transaction of the task write and a rollback leaves none. A new task is `taskCreated`, a write that adds a history event not about a comment is `taskChanged` with `changedProperties` (old and new of each tracked task field), and a comment added, edited or removed between the stored and the written row is `commentCreated`, `commentChanged` or `commentDeleted`. Each event becomes one `OutboxRow` per enabled webhook of the task's board that subscribes to it and whose column filter names the column the task sits in as written (the column it was in, for a delete). The row holds the JSON body serialized once, so delivery sends identical bytes. A webhook keeps at most 1000 rows and 4 MiB of stored row bytes, the oldest dropped first and the newest always kept. Rows count toward no account's stored bytes, so queued events never refuse a write, and they go with their webhook or board.
- `src/db/dispatch.rs`: the outbox side of delivery. `Db::claim_deliveries` reads the oldest due events, removes those whose webhook is gone or disabled, holds each other for a lease by setting its `next_attempt_at`, and returns them as `Delivery` values. It takes at most one event for each webhook and none for a webhook with a delivery in flight, and it drops an event that cannot be decoded together with any index entry left without an event. `finish_delivery` removes an event and `retry_delivery` records a failed try with the time of the next one.
- `src/webhook.rs`: `Dispatcher`, the delivery worker, started in `main.rs` like the disk sampler. Each second it claims due events and sends at most 4 at once on blocking threads and at most one for each webhook (a webhook with a delivery in flight is skipped for that tick), so no request waits on a delivery. It posts the stored body with `X-Pomb-Event` and `X-Pomb-Signature: sha256=<HMAC-SHA256 of the body keyed by the secret>`, follows no redirects, cuts a try off at 10 seconds, retries twice with 5 and 30 second waits and then drops the event. `is_public_address` and `is_public_host` refuse loopback, private, link-local and other non-public targets. The route check applies them to a URL's host at creation and update, and at delivery the agent's resolver `Vetting` resolves the host, refuses the delivery when any address fails the `AddressPolicy` and passes only the vetted addresses to the connector, which keeps the `Host` header and the TLS name. `Dispatcher::with_parts` takes the policy, the lookup and the `Schedule`, which tests replace.
- `src/webhook.rs` also holds `Prober`, which `AppState` carries for the webhook settings screen. It runs the two browser-session checks of `/api/boards/{id}/webhooks/test-dns` and `/test-request` through the delivery agent's resolver, policy and no-redirect, no-proxy, 10 second settings, with its own 2 permits that answer 429 `busy` when taken. The lookup reports only that a host resolves, does not resolve or resolves to a non-public address, and the test request is one unsigned `POST` with `eventType` `test`, `X-Pomb-Event: test` and no `X-Pomb-Signature`. `GET /api/webhooks/{id}/secret` returns a webhook's secret to the browser session only. The screen is the API & Webhooks tab of `templates/board_settings.html`, its Add and Edit pages at `/b/{board_id}/settings/api-webhooks/new` and `/{webhook_id}`, and the `board-settings-webhooks` and `board-settings-webhook-form` pages in `static/pages.js`.
- `src/db/snapshot.rs`: `BoardSnapshot` is one board read through one transaction, and `OfflineDb` a read-only open of the database file for the CLI.
- `src/db/files.rs`: `AttachmentFiles`, the `<database file>.attachments` directory beside the database that holds each attachment's bytes in a file named by its generated UUID (any other id is refused). A write goes to a `.part` file, is flushed and renamed before its row commits, a delete unlinks after its transaction commits, and the startup check removes leftover `.part` files, keeps and reports the files no task names, and reports the tasks whose file is missing. `Db::open` first moves the rows of the old `attachment_data` table into files and deletes the table in one transaction after the last file, and `OfflineDb` refuses a file that still has it. `Incoming` receives an upload chunk by chunk into a `.part` file that is placed only after the last chunk, and a download opens the file and streams it.
- `src/taskjson.rs`: `TaskArray` writes a JSON object ending in a `tasks` array, piece by piece.
- `src/client.rs`: `Client`, a blocking ureq client of a running server built from `POMB_URL` and `POMB_API_TOKEN`. It sends the token as a Bearer header, turns a status of 400 or more into an `Error`, and redacts the token from every error text and its `Debug`.
- `src/board_cli.rs`: the `pomb board` verbs `ls`, `show`, `add`, `move`, `note`, `outcome`, `link`, `label` and `attach`, run before the server starts. `run` returns the text to print. `board_cli/wire.rs` holds the small response structs and `board_cli/table.rs` the aligned plain output.
- `.dev/lua/pomb/lock.lua`: the release lock file `.dev/release.lock` in the main checkout, which `release.lua` takes before its gates and `land.lua` waits on, with the pid check that frees a stale lock, and the land lock `.dev/land.lock`, which `land.lua` takes before its apply and drops after its push to run one land at a time through its gates.
- `.dev/lua/pomb/cargo.lua`: the package version readers for `Cargo.toml` text and the pomb entry of `Cargo.lock` text, shared by `land.lua` and `__version_guard.lua`.
- `.dev/lua/pomb/backup.lua`: the `--backup` argument of `dev verify`, a bare file name or a path under `/var/lib/pomb-backups/`, resolved to the copy's path on green-box and refused otherwise.
- `.dev/lua/pomb/gitenv.lua`: the test git identity and environment (`env`) and the `git` helper that runs git with `-C dir` and trims its output, shared by the dev test files.
- `.dev/lua/pomb/vcs.lua`: the repository reads `dev regress`, `dev lock` and `__gate` share (`stage`, `head`, `merge_base`, `resolve`), through jj when `<root>/.jj` exists and through git otherwise.
- `.dev/lua/pomb/jjenv.lua`: the test fixture that turns a git repository into a jj one, with a `.jj` directory, a `jj` that answers from the git repository and a logging `git`, shared by the dev test files.
- `.dev/tests/`: Lua verb tests named `*_test.lua`, which `dev test` runs after the JS tests through `dev.testrun`, each driving a verb through `dev.testenv`. They run in dev, not in cargo, so the Nix build and `dev nixcheck` never see them.
- `.dev/site/`: the hosting of the public sites, run as `dev site <verb>`. The verbs are `deploy`, `verify`, `status`, `provision`, `launch`, `restage`, `setup-code`, `firewall` and the hidden `decoys`, over ssh through the tunnel name `ssh.pomb.app` with the key `~/.ssh/pomb_app` (`POMB_KEY` overrides it), written in Lua. `.dev/lua/pomb/site.lua` reads the ssh user at run time from `pass show Agents/Linode/pomb.app-host` and never the host, and `firewall` installs an nftables rule that drops new connections to port 22 except on loopback, and `provision` fills the `@ADMIN_IP@` placeholder of `sshd/10-pomb.conf` (the `PerSourcePenaltyExemptList`) from `pass show Agents/Linode/pomb.app-admin-ip` in a staged copy; a missing entry fails the verb, and no address is ever committed. The remote scripts of `status`, `restage`, `setup-code` and `decoys` are the `.sh` files beside them, which each verb reads with `site.read_script` and sends unchanged. The box files are `apt/`, `sshd/`, `systemd/`, `env.in`, plus `.dev/standalone/setup.sh` (the idempotent box setup) and `.dev/standalone/pomb-update`, the pull agent a systemd timer runs as `pomb-update <stable|nightly> [<tag>]`: for a new release it downloads and checks the binary, stops the unit and copies the database to `backups/pomb-<UTC>-before-<id>.redb`, swaps the binary and restarts, and if the health check fails it restores the copy and the previous binary and does not retry that release. Once the unit runs again it runs `pomb archive` on the copy with the previous binary, writing one `.tar.gz` per board into `pomb-<UTC>-before-<id>.archives/` (a binary older than 0.5.30 has no `archive`, and a failure or 60 seconds only logs a warning), and it keeps the last 3 copies with their archive directories. `dev site verify` checks a channel after an update: the public build_sha, `/login` and `/setup`, the CSP and HSTS headers, the journal since the unit started, `last-update-<channel>` and the pre-update backup.
- Report bookmarks: `BoardRow.report_bookmarks` in `src/models.rs` holds a board's saved filter values per chart report (burndown, cumulative-flow, cycle-lead, throughput, monte-carlo, history), each owned by the account that saved it and visible to the others only when shared. `Db::add_report_bookmark`, `update_report_bookmark` and `remove_report_bookmark` change the list in one transaction, and `/api/boards/{id}/report-bookmarks` serves it. The browser side is `ReportTools` in `static/app.js`: the Bookmarks drawer and the PNG, SVG and Excel export that each chart page mounts into `#report-tools`, and `BoardChrome.loadReportShortcuts` lists the bookmarks with a shortcut in the Reports menu.
